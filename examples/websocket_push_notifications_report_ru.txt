[H2] 1 Цель
Цель работы - реализовать в учебном SSR-приложении имитацию push-уведомлений с использованием WebSocket. В рамках работы необходимо было дать клиенту возможность подписываться на уведомления, реализовать серверную рассылку подписанным пользователям и обеспечить отображение входящих сообщений как push-уведомлений через Service Worker или, при невозможности, через стандартный механизм отрисовки уведомлений в интерфейсе.

Реализация анализировалась по последнему коммиту 99f5ba0844c38ff3b2b32f2d30db3be0f0c068fc с сообщением lab 7 done. Коммит добавил отдельный WebSocket-канал для push-событий, клиентский виджет подписок, Service Worker, серверный сервис рассылки и административную страницу отправки уведомлений.

[H2] 2 Задачи
Для достижения цели были поставлены следующие задачи: изучить текущую структуру Express и EJS-приложения; подключить отдельный WebSocket endpoint для push-уведомлений; реализовать хранение подписок клиента на выбранные темы; добавить серверную рассылку только тем WebSocket-подключениям, которые подписаны на соответствующий топик; создать интерфейс администратора для отправки уведомлений; реализовать отображение уведомлений через Service Worker и Notification API; предусмотреть fallback-режим для браузеров без разрешения на системные уведомления; интегрировать новую функциональность в общий интерфейс приложения.

[H2] 3 Ход работы
Работа выполнялась на базе существующего учебного интернет-магазина SSR Store, построенного на Node.js, Express и EJS. До выполнения задания в проекте уже существовал HTTP-сервер, cookie-сессии, шаблоны страниц и WebSocket-чат. Последний коммит расширил эту архитектуру отдельным каналом push-уведомлений, сохранив единый порт приложения и общую систему сессий.

[H3] 3.1 Анализ требований и выбранного подхода
Задание требовало имитации push-уведомлений через WebSocket. Поэтому в реализации не использовался полноценный Web Push Protocol с внешним push-сервисом и VAPID-ключами. Вместо этого браузер поддерживает постоянное WebSocket-соединение с сервером, а сервер по этому соединению отправляет событие push. Такой подход подходит для учебной задачи, потому что позволяет показать подписку, адресную рассылку по темам и пользовательское отображение уведомления без подключения сторонней инфраструктуры.

Для разделения потоков данных был создан отдельный endpoint ws://localhost:3000/ws/push. Он не смешивается с ранее реализованным WebSocket-чатом ws://localhost:3000/ws/chat, поэтому логика уведомлений не влияет на комнаты чата и историю сообщений. В README добавлено описание новой подсистемы: доступные топики, виджет-колокольчик, Service Worker, административная страница рассылки и fallback-режим в виде toast-сообщения.

[H3] 3.2 Реализация серверного WebSocket-канала
Серверная часть вынесена в файл src/websocket/pushServer.js. Модуль создает WebSocketServer с параметром noServer: true и обрабатывает событие upgrade основного HTTP-сервера. При upgrade проверяется путь запроса: push-соединения принимаются только на /ws/push. Дополнительно выполняется проверка Origin: если заголовок присутствует, его host должен совпадать с host текущего запроса.

В src/server.js основной Express app оборачивается в http.createServer. После этого подключаются два WebSocket-сервера: существующий чат и новый push-сервер. Для push-канала вызывается attachPushServer(server, sessionMiddleware), затем результат регистрируется в pushService через pushService.register(push). Благодаря этому HTTP-маршруты могут инициировать рассылку, не зная деталей хранения WebSocket-подключений.

При подключении к push-серверу применяется существующий sessionMiddleware. Если пользователь авторизован, сервер берет данные из req.session.user. Если сессии нет, подключение все равно разрешается в гостевом режиме, а пользователю назначается id вида guest-UUID и имя вида Гость-XXXX. Каждому соединению присваивается socketId через randomUUID, сохраняются пользователь, IP-адрес, время подключения, набор подписок и флаг isAlive для heartbeat-проверки.

[H3] 3.3 Организация подписок клиента
На сервере определен закрытый список допустимых топиков: promotions, orders, news и system. Клиент отправляет сообщения в формате JSON с полями type и payload. Для подписки используется событие subscribe, в котором payload.topics содержит массив выбранных топиков. Сервер проверяет, что массив состоит только из допустимых строк, удаляет дубликаты и записывает результат в ws.topics.

После успешной подписки сервер отправляет клиенту событие subscribed с актуальным списком топиков. Также реализованы события unsubscribe и get_state. unsubscribe удаляет указанные топики из текущего набора подписок, а get_state позволяет клиенту запросить состояние подписок повторно. Невалидный JSON, отсутствие type, неизвестный тип события или недопустимые топики приводят к отправке события error с кодом ошибки.

Клиентская часть подписки реализована в public/scripts/push/push-client.js и разметке views/partials/push-widget.ejs. Виджет расположен в правом нижнем углу сайта и содержит кнопку открытия, статус соединения, статус разрешения браузера, четыре checkbox-поля топиков, кнопку сохранения и кнопку тестового уведомления. Выбранные топики сохраняются в localStorage по ключу push.topics, поэтому после перезагрузки страницы интерфейс восстанавливает прежний выбор.

[H3] 3.4 Рассылка уведомлений подписанным пользователям
Рассылка выполняется через сервис src/services/pushService.js. Он хранит ссылку на API push-сервера и предоставляет метод broadcast(topic, notification). Внутри pushServer.js метод broadcast проверяет существование топика, нормализует заголовок, текст и URL уведомления, формирует сообщение с id и sentAt, затем проходит по всем активным WebSocket-подключениям.

Событие push отправляется только тем соединениям, у которых ws.topics содержит выбранный топик и сокет открыт. Для каждого успешного отправления увеличивается счетчик delivered. Метод возвращает объект с количеством получателей и отправленным сообщением. Такой механизм реализует основное требование задания: сервер умеет делать рассылку подписанным пользователям, а пользователи без подписки на выбранный топик сообщение не получают.

Для запуска рассылки добавлена административная страница /admin/notify. Маршруты находятся в src/routes/adminRoutes.js и защищены middleware requireAdmin. GET-запрос отображает форму с выбором топика, заголовком, текстом и необязательным URL. POST-запрос валидирует поля, проверяет допустимость топика, ограничивает длину заголовка, текста и URL, после чего вызывает pushService.broadcast. После отправки пользователь перенаправляется обратно на страницу с сообщением о количестве получателей.

[H3] 3.5 Отображение push-уведомлений на клиенте
Для отображения системных уведомлений добавлен Service Worker public/sw.js. Он устанавливается клиентским скриптом через navigator.serviceWorker.register('/sw.js', { scope: '/' }). В src/app.js для файла /sw.js создан отдельный маршрут, который выставляет заголовок Service-Worker-Allowed: /, отключает кэширование и отдает JavaScript-файл из public.

Когда клиент получает WebSocket-событие push, функция handleIncomingPush проверяет поддержку Notification API и наличие разрешения granted. Если разрешение выдано и Service Worker активен, клиент передает уведомление в worker через postMessage с type: push. Service Worker принимает это сообщение, извлекает title, body, tag и url, затем вызывает self.registration.showNotification. При клике по уведомлению обработчик notificationclick закрывает уведомление, ищет уже открытое окно с нужным путем и фокусирует его либо открывает новое окно.

Если Notification API недоступен, пользователь запретил уведомления или Service Worker не смог отработать, используется fallback. Скрипт создает DOM-элемент push-toast в верхней части страницы, выводит заголовок и текст уведомления, а при наличии URL делает toast кликабельным. Это сохраняет функциональность даже в браузерах или состояниях, где системные push-уведомления невозможны.

[H3] 3.6 Интеграция в интерфейс и управление доступом
Новый виджет подключен глобально через views/partials/footer.ejs, поэтому он доступен на всех страницах приложения. Стили виджета, toast-уведомлений и страницы администратора вынесены в public/styles/push.css и подключены в views/partials/head.ejs. В header добавлена ссылка Рассылка, но она отображается только авторизованным пользователям с флагом isAdmin.

Для сохранения административного признака изменены src/services/userService.js и src/services/sessionService.js. Функция toSafeUser теперь добавляет в безопасный объект пользователя поле isAdmin, а signInSession сохраняет пользователя в сессии через toSafeUser. Middleware requireAdmin проверяет req.session.user.isAdmin и запрещает доступ к странице рассылки пользователям без административных прав.

[H3] 3.7 Устойчивость соединения и обработка ошибок
На клиенте реализовано автоматическое переподключение. Если WebSocket закрывается не по инициативе пользователя, скрипт планирует повторное подключение с нарастающими задержками 1, 2, 4, 8 и 16 секунд. Исходящие сообщения помещаются в очередь, если сокет еще не открыт, и отправляются после восстановления соединения. При повторном открытии соединения клиент заново отправляет сохраненные в localStorage подписки.

На сервере реализована heartbeat-проверка активных клиентов с интервалом 30 секунд. Сервер отправляет ping, ожидает pong и завершает соединения, которые перестали отвечать. При SIGINT или SIGTERM в src/server.js закрываются чат и push-сервер, затем останавливается HTTP-сервер. Это позволяет корректно освободить WebSocket-подключения при остановке приложения.

[H3] 3.8 Проверка результата
Проверка реализации выполнялась по изменениям последнего коммита и по соответствию кода требованиям задания. Клиент имеет возможность подписаться на уведомления через виджет и сохранить выбранные топики. Сервер хранит подписки в памяти активных WebSocket-подключений и рассылает сообщения только подписанным клиентам. Отображение уведомлений реализовано через Service Worker и Notification API, а для случаев без системных уведомлений предусмотрен in-page toast.

Для ручной проверки пользователь может открыть сайт, нажать кнопку Уведомления, выбрать один или несколько топиков и сохранить подписки. Администратор может перейти на /admin/notify, выбрать тот же топик, заполнить заголовок и текст, после чего отправить рассылку. Подписанный клиент должен получить системное уведомление или toast-сообщение, а неподписанные клиенты не должны получить это событие.

[H2] 4 Вывод
В результате работы была реализована имитация push-уведомлений на основе WebSocket. Клиентская часть получила интерфейс подписки, хранение выбранных тем, автоматическое переподключение, регистрацию Service Worker и fallback-отрисовку уведомлений. Серверная часть получила отдельный WebSocket endpoint /ws/push, учет активных подключений, проверку подписок, heartbeat, сервис broadcast и административную страницу рассылки.

Поставленные задачи выполнены: клиент может подписываться на уведомления, сервер может отправлять сообщения подписанным пользователям, а браузер отображает входящие уведомления через Service Worker или через стандартный интерфейс страницы. Реализация соответствует формату учебной имитации push-механизма и демонстрирует полный цикл обмена: подписка клиента, серверная рассылка и визуальное получение уведомления пользователем.
