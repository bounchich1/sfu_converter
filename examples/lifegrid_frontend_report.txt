[H1] Отчет о frontend части проекта LifeGrid

[H2] Постановка задачи

[H3] Назначение проекта
LifeGrid представляет собой web-приложение для управления личной и командной работой: рабочими пространствами, проектами, дорожными картами, задачами, статусами, участниками, профилем пользователя и аналитическими сводками. В текущем состоянии frontend реализован как одностраничное приложение на React и TypeScript, а продуктовая область охватывает как индивидуальную продуктивность, так и командную координацию.

Задача frontend части состоит в том, чтобы предоставить пользователю единый интерфейс для планирования, декомпозиции и контроля работы. Пользователь должен видеть доступные рабочие пространства, переключаться между ними, создавать и обновлять задачи, связывать задачи с дорожными картами, отслеживать состояние выполнения, управлять профилем и получать агрегированную картину прогресса на dashboard.

[H3] Роль frontend в системе
Frontend является клиентским слоем, который связывает пользовательские сценарии с backend API. Он отвечает за маршрутизацию, авторизацию, хранение клиентского состояния, кэширование серверных данных, отображение форм, модальных окон, уведомлений, drag-and-drop взаимодействий, rich text редактирование и локализацию интерфейса.

Фактическая кодовая база отличается от целевого описания в корневом README. Текущая реализация использует SteroidsJS, webpack-сборку, Redux через reducers SteroidsJS, TanStack Query v4 и SCSS. Это важно для отчета, потому что фактическая архитектура должна описываться по исходному коду и текущим спецификациям из docs/current-state, а не только по целевому PRD.

[H3] Основные пользовательские сценарии
Первый базовый сценарий связан с входом в систему. Пользователь открывает landing page, переходит к авторизации, входит через email и пароль либо через Google/Yandex OAuth, после чего приложение получает токены и инициализирует сессию через /auth/init.

Второй сценарий связан с рабочими пространствами. Пользователь попадает в workspace shell, видит список проектов, участников и дополнительные разделы workspace. Если пользователю доступно несколько рабочих пространств, он выбирает активное пространство, а API-запросы должны выполняться с учетом workspace_id.

Третий сценарий связан с Kanban-доской задач. Пользователь видит задачи, сгруппированные по статусам, создает новые задачи, задает описание, срок, дорожную карту и теги, а также переносит карточки между колонками. Перенос карточки должен сохраняться на backend через обновление note/status.

Четвертый сценарий связан с дорожными картами. Пользователь просматривает timeline, видит месяцы, недели и группы roadmaps, создает и редактирует дорожные карты, связывает с ними задачи и использует timeline как визуальный инструмент планирования.

Пятый сценарий связан с настройками и профилем. Пользователь редактирует имя пользователя, email, язык интерфейса, аватар и перспективно расширенные профильные поля.

[H3] Границы отчета
Настоящий отчет фокусируется на frontend части. Серверные разделы включены в структуру документа по заданному плану, но содержательно не раскрываются. В них оставлены заголовки для последующего заполнения backend командой.

[H2] Выборка требований (описание конкурентов и тд)

[H3] Источники требований
Основными источниками требований являются документы docs/current-state, docs/todo, backend-api-needs-from-frontend.md и корневой README. Документы current-state описывают фактическую реализацию на дату 11.05.2026. Документы todo описывают план выравнивания frontend с обновленным backend API: нормализацию ответов, активный workspace, roadmaps, notes, labels, statuses, projects, members, dashboard и time tracking.

Корневой README используется как целевой PRD, но не как точное описание текущего кода. В нем обозначены React, TypeScript, Feature-Sliced Design, Redux Toolkit, TanStack Query v5, Shadcn UI и Zod, однако фактическая реализация сейчас построена на SteroidsJS, TanStack Query v4, SCSS и route-oriented структуре.

[H3] Функциональные требования к авторизации
Frontend должен поддерживать вход по email и паролю, регистрацию, Google OAuth, Yandex OAuth, callback-страницы, извлечение accessToken и refreshToken в snake_case и camelCase форматах, запуск SteroidsJS login и fallback-инициализацию через /auth/init.

Важным требованием является устойчивость к переходному API-контракту. Backend может возвращать access_token или accessToken, refresh_token или refreshToken. Поэтому frontend содержит helper-функции для нормализации токенов и defensive fallback для ролей авторизованного пользователя.

[H3] Функциональные требования к рабочим пространствам
Приложение должно поддерживать список рабочих пространств, активное workspace, сохранение выбранного workspace в localStorage, выбор default_workspace_id из /auth/init и применение workspace_id в запросах задач, статусов, дорожных карт, проектов, участников, dashboard и time tracking.

Для пользователей с несколькими рабочими пространствами требуется явный selector. Для пользователей с одним рабочим пространством интерфейс может отображать его имя без dropdown, но API-слой все равно должен работать с явным идентификатором, чтобы исключить неоднозначность и зависимость от backend fallback.

[H3] Функциональные требования к задачам
Задачи реализуются как notes backend-модели. Frontend должен загружать статусы и notes, группировать notes по status_id, строить Kanban-колонки, создавать задачи с title, content, deadline, roadmap_id, status_id, workspace_id и labels, а также обновлять status_id при drag-and-drop перемещении карточки.

Требуется поддержка rich text описания задачи. Для этого используется Tiptap Markdown field, который сериализует содержимое в Markdown и передает его как content. В перспективе labels должны стать полноценными API-backed тегами, а не пустым списком в Kanban.

[H3] Функциональные требования к дорожным картам
Roadmaps должны загружаться с backend, фильтроваться или запрашиваться в контексте workspace, отображаться на timeline с месяцами и неделями, рассчитывать смещение и длительность по started_at и deadline, показывать вложенные задачи и поддерживать создание/редактирование через modal.

Плановый API-контракт требует поддержки status, note summaries, options endpoint, delete endpoint и отказа от transitional users_id в новых payload. Текущий frontend уже передает workspace_id, но в create payload пока сохраняется users_id, что следует рассматривать как технический долг.

[H3] Функциональные требования к dashboard
Dashboard сейчас является статическим mock-интерфейсом. Требования из docs/todo предусматривают замену hardcoded карточек, random heatmap и статического timer на endpoint /dashboard/summary с workspace_id и периодом. Dashboard должен показывать roadmaps total/completed/active/paused, task completion, activity heatmap, progress series, bar series и time tracking агрегаты.

[H3] Функциональные требования к профилю и настройкам
Settings page должен редактировать username, email, язык интерфейса, avatar upload и avatar delete. Более полный профиль должен поддерживать name, surname, login, role, bio, locale и timezone через /user/profile. Профильная страница сейчас является placeholder, поэтому требование к ней относится к будущему развитию.

[H3] Нефункциональные требования
Frontend должен быть типизирован на TypeScript, использовать React 18 functional components, поддерживать клиентскую маршрутизацию, обеспечивать стабильную работу с API-ошибками, разделять server state и client state, иметь unit/component тесты, e2e smoke/flow тесты, lint/build pipeline и локализацию на русский и английский языки.

Отдельное нефункциональное требование связано с поддерживаемостью. Текущая структура является route-oriented, поэтому новые изменения должны сохранять локальные паттерны: route modules в src/routes, shared-компоненты в src/shared, низкоуровневые виджеты и view overrides в src/ui, глобальные constants/config/providers/reducers отдельно.

[H3] Ограничения и риски требований
Первый риск связан с рассинхронизацией README и фактической реализации. Если разработчик ориентируется только на README, он может ошибочно ожидать Vite, Shadcn UI, Redux Toolkit и strict FSD. Для текущих задач baseline должен браться из docs/current-state.

Второй риск связан с API-контрактом. Backend уже описывает больше возможностей, чем потребляет frontend. Часть endpoints и схем еще не подключена к UI: workspace projects, members/invites, dashboard summary, time tracking, labels/options, richer profile fields.

Третий риск связан с качеством. TypeScript strict не включен, отдельного typecheck script нет, CI не запускает unit/e2e тесты, а e2e зависят от локального frontend сервера, backend и WebDriver окружения.

[H2] Описание клиентской части - какие технологии, архитектура, обработка ошибок

[H3] Технологический стек frontend
Frontend построен на React 18 и TypeScript 4.9. Приложение использует @steroidsjs/core как инфраструктурную основу: bootstrapping, routes, layout, auth helpers, HTTP component, forms, Redux integration, modals, notifications и locale component. Для UI-компонентов используется @steroidsjs/bootstrap, а кастомные views регистрируются через локальный bootstrap.ts.

Server state управляется через TanStack React Query v4. Глобальное клиентское состояние представлено Redux reducers SteroidsJS и кастомным reducer для Kanban. Стили реализованы на SCSS с глобальными imports и BEM-подобными классами через useBem. Для rich text применяется Tiptap 3 с Markdown serialization. Drag-and-drop Kanban основан на react-beautiful-dnd.

[H3] Сборка и окружение
Сборка выполняется через @steroidsjs/webpack. Команда yarn watch запускает локальный dev server на 9991 порту, yarn build собирает production bundle, yarn lint запускает ESLint, yarn test запускает Jest, yarn test:e2e запускает Selenium e2e через отдельный Jest config.

Frontend читает APP_BACKEND_URL из environment и передает его в JwtHttpComponent. В текущем окружении это ключевой параметр, потому что все API-запросы строятся относительно backend URL. Документация отмечает, что .env.example пустой, поэтому onboarding новых разработчиков требует доработки.

[H3] Точка входа приложения
src/index.tsx создает React root и оборачивает Application в QueryProvider. src/Application.tsx описывает config для SteroidsJS: reducers, routes, layoutView, locale component, JwtHttpComponent, translations, icon registry, form fields, formatters и custom UI views.

[H3] Архитектурная организация исходного кода
Код организован прагматично, вокруг route modules. src/routes содержит страницы и feature-specific hooks/types/views. src/shared содержит переиспользуемые application-level компоненты: Layout, Sidebar, Header, WorkspaceShell, Card, auth forms, FilterButton, ColorPickerField. src/ui содержит lower-level widgets и custom Steroids views: Kanban, KabnanLogic, Modal, TiptapMarkdownField, form overrides.

Инфраструктурные элементы вынесены в src/consts, src/config, src/providers, src/reducer, src/locales, src/style, src/types и src/utils. Такая структура не является strict Feature-Sliced Design, но она уже используется в проекте и должна сохраняться до отдельного архитектурного рефакторинга.

[H3] Маршрутизация
Маршруты описаны как SteroidsJS IRouteItem и собираются в src/routes/index.ts. Приложение содержит группы auth, dashboard, tasks, roadmaps, workspace, settings и profile. Route IDs централизованы в src/consts/routes.ts, что уменьшает риск строковых расхождений при переходах и проверках active state.

Правила доступа задаются на уровне маршрутов. Landing/root route доступен анонимным и авторизованным пользователям. Auth routes доступны анонимным пользователям. Dashboard, tasks, roadmaps, settings, profile и workspace требуют PermissionsEnum.AUTH_AUTHORIZED.

[H3] Layout и shell-структура
Глобальный Layout вызывает /auth/init через useLayout, ожидает завершения инициализации и отображает Sidebar для авторизованных non-workspace маршрутов. Для workspace routes используется full-width wrapper, а сами workspace pages оборачиваются в WorkspaceShell.

WorkspaceShell предоставляет отдельный sidebar с логотипом, summary пользователя, selector активного workspace, workspace navigation и logout. Такое разделение оправдано: обычные продуктовые разделы и workspace management имеют разные навигационные модели.

[H3] Управление server state
Для API-backed данных используются React Query hooks. QueryProvider задает единые настройки: отключенный refetchOnWindowFocus, staleTime 3000 ms и retry false. Это делает поведение предсказуемым во время разработки и тестирования: ошибки не маскируются автоматическими повторными запросами, а данные не обновляются при каждом фокусе окна.

[IMAGE=lifegrid_code_02_query_provider.png]
Рисунок 3 - Настройка TanStack Query provider

Query keys централизованы в src/consts/query-keys.ts. Там определены ключи для auth-init, workspaces, workspace, statuses, notes, roadmaps, labels, projects, members, dashboard summary и current time tracking. Это важный шаг к предотвращению коллизий кэша между разными workspace.

[H3] Управление client state
Redux используется через SteroidsJS reducers: form, auth, fields, list, notifications, modal и router. Дополнительно проект содержит кастомный kanban reducer, где состояние досок хранится по kanbanId: columns, tags и lastTaskId. Такой подход позволяет использовать один Kanban logic layer для разных досок, если каждая доска имеет уникальный id.

[H3] API-слой
API constants собраны в src/consts/api.ts. Там описаны группы AUTH_API, WORKSPACES_API, USER_API, STATUSES_API, NOTES_API, ROADMAPS_API и PROJECTS_API. Формат API constants простой: METHOD и URL, где URL может быть строкой или функцией от идентификатора.

Преимущество этого подхода - централизованность endpoint строк. Ограничение - тип URL функции допускает any[] в createApi, поэтому сигнатуры API не полностью типобезопасны. Для дальнейшего развития лучше усилить типизацию API constants и постепенно убрать дублирование endpoint-ов, например local TASKS_API.CREATE_TASK в TasksPage.

[H3] Обработка ошибок
Проект содержит utils/apiErrors.ts и utils/apiResponse.ts для нормализации неоднородных API-ответов. Это важно, потому что backend может возвращать ошибки в разных формах: status_code/errors, detail/status_code/errors, success:false, а иногда 200 response с errors без data.

apiErrors.ts извлекает statusCode, errors и response, формирует ApiError и бросает исключение через throwIfApiError. apiResponse.ts предоставляет unwrapApiData и assertApiSuccess. unwrapApiData возвращает response.data из envelope вида {success, message, data}, а bare arrays или bare objects возвращает как есть.

[H3] Drag-and-drop обновление статуса задачи
Drag-and-drop основан на react-beautiful-dnd. Если destination отсутствует, обработчик ничего не делает. Если source column отличается от target column, TasksPage находит note по draggableId, собирает payload с title, content, status_id и workspace_id, отправляет PUT /notes/{noteId}, затем invalidates notes query.

С точки зрения UX это правильная модель: оптимальное поведение может быть дополнено optimistic update, но уже сейчас после successful backend update данные перезапрашиваются и Kanban приходит к server-truth состоянию.

[H3] Обработка API envelopes в реализации
На практике frontend должен работать как с bare arrays, так и с envelope responses. Например, list endpoints могут вернуть массив, а create/update endpoints - объект с data. Поэтому в hooks используются assertApiSuccess и unwrapApiData. Это уменьшает дублирование проверок в компонентах и делает ошибочные ответы исключениями, совместимыми с React Query onError.

[H2] Тестирование - покрытие тестами, unittest'ы, e2e

[H3] Общая стратегия тестирования
Проект использует Jest для unit/component тестов и отдельный Jest config для Selenium e2e. Unit tests выполняются в jsdom environment, e2e tests - в Node environment. Testing Library используется для React component tests. SCSS мапится на identity-obj-proxy, lodash-es мапится на lodash, а setupTests задает глобальную функцию перевода __.

[H3] Unit и component tests
Unit/component tests размещены рядом с исходным кодом в src/**/*.test.ts и src/**/*.test.tsx. Покрыты shared-компоненты, hooks, utils, route-level pages и UI-компоненты. Среди тестируемых областей: AuthorizationForm, Card, ColorPickerField, FilterButton, Header, Layout, Sidebar, WorkspaceShell, WorkspaceProjectsPage, WorkspaceMembersPage, WorkspacePricingPage, WorkspaceHistoryPage, Settings hooks, Roadmaps hooks/modal, KanbanView, apiErrors и apiResponse.

Команда запуска: yarn test. В package.json она соответствует jest. Текущая конфигурация запускает тесты в один worker и с single concurrency, что делает результаты более стабильными, но увеличивает время выполнения на большой test suite.

[H3] E2E tests
E2E tests находятся в e2e/auth.e2e.ts, e2e/example.e2e.ts и e2e/roadmaps.e2e.ts. Они используют Selenium WebDriver, ожидают frontend на http://127.0.0.1:9991 и требуют работающий backend. Текущие e2e flows: открыть приложение и проверить root, зарегистрироваться/выйти/войти, войти и создать roadmap.

Команда запуска: yarn test:e2e. Перед ней обычно требуется yarn watch, а также backend и браузерный driver. Поэтому эти тесты сложнее запускать в CI без подготовленного окружения.

[H3] Проверка качества через lint и build
Lint запускается командой yarn lint и использует @steroidsjs/eslint-config/frontend с локальными overrides. Build запускается командой yarn build и использует node webpack production. GitLab CI содержит lint и build stages, но не запускает yarn test и yarn test:e2e.

[H3] Покрытие тестами
В проекте нет отдельного coverage script и coverage thresholds. Формально покрытие можно получить через yarn test --coverage, но это создаст coverage artifacts. Документация current-state отмечает, что broad coverage для task creation/update flows, settings mutations, roadmap timeline calculations и dashboard отсутствует или недостаточна.

[H3] Примеры тестируемых рисков
apiErrors.test.ts и apiResponse.test.ts важны для защиты от неоднородных backend responses. useActiveWorkspace.test.ts должен проверять выбор active workspace, fallback на default workspace и saved workspace. useTasksData.test.ts и useRoadmaps.test.ts проверяют workspace-scoped запросы и invalidation. Component tests workspace pages проверяют UI states и фильтрацию static/project data.

[H3] Текущие пробелы в качестве
Первый пробел - отсутствие TypeScript strict и отдельного tsc --noEmit скрипта. Это увеличивает риск runtime ошибок в API integration коде, особенно там, где используются any и нестрогие backend response shapes.

Второй пробел - CI не запускает unit/e2e tests. Это означает, что merge может пройти lint/build, но сломать behavior. Минимальный следующий шаг - добавить yarn test в CI после lint или build. E2E следует подключать отдельно, когда будет стабильный test backend.

Третий пробел - часть UI работает на mock/static data. Для таких областей тесты проверяют rendering, но не реальные API state transitions. После подключения backend endpoints нужно добавить tests на loading/error/empty/success states и mutations.

[H3] Рекомендации по развитию тестирования
Рекомендуется ввести coverage command и минимальные thresholds сначала для utils/hooks, затем для route-level logic. Для Kanban нужно покрыть создание задачи, drag-and-drop update, invalidation и rollback/error scenarios. Для roadmaps - timeline calculations, empty state, invalid dates и create/update payloads. Для settings - avatar upload/delete, profile update и API error mapping.

Для e2e рекомендуется выделить deterministic test data и test backend seed. Текущие e2e зависят от окружения, поэтому они полезны для ручной регрессии, но пока не являются надежным CI gate.
