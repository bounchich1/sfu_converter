[H1] Отчет о выполненной мной frontend части проекта LifeGrid

[H2] Постановка задачи

[H3] Цель выполненной работы
Цель моей работы заключалась в разработке и доработке frontend части web-приложения LifeGrid. Я работал с клиентским приложением на React и TypeScript, настраивал базовую инфраструктуру проекта, подключал пользовательские сценарии к backend API, развивал workspace-разделы и реализовывал интерфейсы для задач, дорожных карт, проектов, тарифов, интеграций и истории действий.

Отчет является frontend-only документом. В нем описывается только клиентская часть, то есть маршрутизация, формы, пользовательский интерфейс, hooks, клиентское состояние, запросы к API, обработка ошибок и тесты. Серверная реализация, база данных и backend бизнес-логика намеренно не рассматриваются, за исключением краткого упоминания API-контрактов, с которыми взаимодействует frontend.

[H3] Границы личного вклада
В рамках проекта мной были выполнены boilerplate и базовая конфигурация приложения, обычная аутентификация через email и пароль, workspace navigation и workspace creation flow, подготовка API-слоя для проектов, развитие roadmaps, Kanban-страница задач и механика редактирования, а также отдельные workspace-разделы: integrations, paid plans и history logs.

OAuth-сценарии не включены в этот отчет как часть моего описания. В разделе аутентификации я описываю только регистрацию, вход по email и паролю, извлечение accessToken/refreshToken, инициализацию пользовательской сессии и защиту авторизованных маршрутов.

[H3] Пользовательские сценарии, которые закрывает frontend
Первый сценарий - запуск приложения и вход пользователя через форму авторизации. Пользователь вводит email и пароль, frontend отправляет запрос на backend, извлекает токены из ответа и переводит пользователя в авторизованную область приложения.

Второй сценарий - выбор или создание рабочего пространства. Пользователь видит список доступных workspaces, может создать новое пространство через wizard, пригласить участников и перейти в выбранное рабочее пространство.

Третий сценарий - работа с проектами внутри workspace. Пользователь видит карточки проектов, может искать проекты, а API-слой содержит подготовленные hooks для списка, создания, обновления и удаления проектов в контексте активного workspace.

Четвертый сценарий - планирование через roadmaps. Пользователь открывает timeline, видит дорожные карты по месяцам и неделям, создает новую дорожную карту и редактирует существующую.

Пятый сценарий - управление задачами на Kanban-доске. Пользователь видит статусы как колонки, создает задачу через modal, заполняет rich text описание, выбирает deadline и дорожную карту, а затем переносит задачу между колонками.

Шестой сценарий - административные разделы workspace. Пользователь может просматривать интеграции, включать или отключать сервисы на уровне UI, выбирать тарифный план и анализировать историю действий через фильтры и поиск.

[H2] Требования к frontend части

[H3] Функциональные требования
Frontend должен предоставлять пользователю связный интерфейс для личной и командной работы. Основная модель приложения строится вокруг рабочей области, проектов, дорожных карт, задач, статусов и административных разделов. Поэтому клиентская часть должна уметь определять активный workspace и передавать workspace_id в запросы, где это требуется API-контрактом.

Аутентификация должна поддерживать вход и регистрацию через форму, а также сохранять refresh token для последующего обновления сессии. Так как backend может возвращать токены в snake_case или camelCase формате, frontend должен нормализовать ответы и не зависеть от одного варианта поля.

Roadmaps должны отображаться как timeline, где видны месяцы, недели, длительность дорожной карты и связанные задачи. Пользователь должен иметь возможность открыть modal создания или редактирования roadmap, задать название, описание, deadline и цвет.

Kanban должен показывать статусы как колонки и notes как карточки задач. При создании задачи frontend должен передавать title, content, deadline, roadmap_id, status_id и workspace_id. При перемещении карточки между колонками frontend должен обновлять status_id задачи на backend.

Workspace-раздел должен включать проекты, участников, историю, тарифы и интеграции. Даже если часть данных пока является static/mock слоем, UI должен быть построен так, чтобы его можно было подключить к API без полной переработки страницы.

[H3] Нефункциональные требования
Клиентская часть должна оставаться типизированной, компонентной и поддерживаемой. Для server state используется TanStack Query, для глобального клиентского состояния - Redux через reducers SteroidsJS, для форм - компоненты SteroidsJS, для стилей - SCSS с BEM-подобными именами классов.

Запросы должны иметь единые query keys и явную invalidation-стратегию после mutations. Ошибочные API responses должны превращаться в понятные frontend errors и notification messages, чтобы пользователь видел не технический stack trace, а конкретную проблему.

Проект должен поддерживать базовую проверку качества: lint, production build, unit/component tests и отдельные e2e-сценарии. Отдельная задача качества - не смешивать mock UI с API-backed кодом без явного разграничения, чтобы в дальнейшем было понятно, какие части готовы к production-интеграции, а какие являются UI прототипом.

[H3] Требования к личному отчету
Отчет должен описывать не абстрактную систему, а выполненную мной работу. Поэтому в последующих разделах я описываю конкретные frontend решения: какие файлы и модули были задействованы, как устроены hooks, какие данные проходят через формы, где используются placeholders, и какие ограничения остались после реализации.

[H2] Boilerplate и базовая конфигурация

[H3] Entry point и корневой Application config
Точка входа приложения находится в src/index.tsx. Она создает React root через react-dom/client, оборачивает Application в QueryProvider и монтирует приложение в DOM-элемент root. Такой entrypoint отделяет инфраструктуру React Query от SteroidsJS application config и делает server-state provider доступным для всех route-level hooks.

Основной конфиг приложения описан в src/Application.tsx. В нем подключены reducers, route tree, layout, locale component, JWT HTTP component, UI bootstrap, form fields, formatters и SVG icons. Я использовал этот файл как центральное место, где приложение собирается из инфраструктурных частей.

[H3] QueryProvider и server-state поведение
Для серверного состояния используется TanStack Query v4. QueryClient настроен с refetchOnWindowFocus: false, staleTime 3000 ms и retry: false. Эти настройки делают интерфейс менее шумным во время разработки: данные не перезапрашиваются при каждом фокусе окна, ошибки не повторяются автоматически, а небольшое stale window уменьшает количество лишних запросов.

QueryProvider также использует QueryErrorResetBoundary. Это полезно для будущей обработки ошибок в route-level boundary, потому что состояние ошибки query можно будет сбрасывать централизованно, не переписывая каждый hook вручную.

[H3] Маршрутизация и layout
Маршруты собраны в src/routes/index.ts и разделены по route groups: auth, dashboard, tasks, roadmaps, workspace, settings и profile. Для защищенных страниц используется PermissionsEnum.AUTH_AUTHORIZED. Это позволяет отделить public landing/auth routes от рабочей области приложения.

Глобальный Layout отвечает за инициализацию пользователя через /auth/init, проверку прав доступа и отображение default sidebar. Workspace routes используют отдельный WorkspaceShell, потому что рабочее пространство имеет собственную навигационную модель: projects, members, history, pricing и integrations.

[H3] Сборка, окружение и CI
Проект использует webpack.js поверх @steroidsjs/webpack. В конфигурации включены inline SVG, dev server на порту 9991, hot reload, watch polling и ESM compatibility rule для fullySpecified: false. Переменная APP_BACKEND_URL читается из окружения и передается в JwtHttpComponent как backend base URL.

В package.json описаны основные команды: yarn watch, yarn build, yarn lint, yarn test и yarn test:e2e. GitLab CI содержит lint, build и deploy stages. На build stage выполняется production-сборка, а public/ используется как artifact и основа для dev deploy.

[H2] Authentication без OAuth

[H3] Форма входа
В обычной аутентификации реализована форма входа по email и паролю. AuthorizationForm построен на SteroidsJS Form, InputField и Button. Форма отправляет POST-запрос на /auth/login и после успешного ответа передает управление callback-функции onComplete в AuthPage.

AuthPage извлекает accessToken и refreshToken из ответа и вызывает login из SteroidsJS auth actions. После этого пользователь переводится в dashboard, а refreshToken передается в JWT-компонент, чтобы приложение могло поддерживать сессию после обновления access token.

[IMAGE]
Рисунок 3 - Место для скриншота формы входа по email и паролю

[H3] Форма регистрации и проверка пароля
RegistrationForm содержит поля username, email и password. Для пароля реализована локальная проверка силы: минимальная длина, строчная буква, заглавная буква и цифра. По количеству выполненных условий рассчитывается percent для ProgressBar, а список требований отображается рядом с полем.

Такой подход не заменяет backend validation, но улучшает UX: пользователь заранее видит, какие требования к паролю не выполнены. После успешной регистрации используется тот же onComplete flow, что и для login, поэтому вход и регистрация приводят к единой логике установки сессии.

[H3] Нормализация токенов и initialization fallback
Backend может вернуть токены в разных форматах: access_token или accessToken, refresh_token или refreshToken. Для этого в src/routes/auth/utils/tokens.ts реализованы extractAccessToken и extractRefreshToken. Эти функции перебирают допустимые ключи и возвращают только непустую строку.

В Application config также реализована normalizeAuthInitResponse. Если backend возвращает authenticated user без roles, frontend добавляет PermissionsEnum.AUTH_AUTHORIZED как defensive fallback. Это снижает риск, что пользователь успешно прошел login, но затем не может открыть защищенные маршруты из-за неполного init response.

[H2] Workspace creation и активное рабочее пространство

[H3] Список рабочих пространств
Для загрузки рабочих пространств реализован useWorkspaces. Hook отправляет GET /workspaces/ и unwrap-ит data через unwrapApiData. Query key вынесен в queryKeys.workspaces, поэтому связанные mutations могут инвалидировать список без ручного повторения строковых ключей.

Страница /workspaces показывает пользователю доступные рабочие области и карточку создания нового workspace. Карточки отображают название, описание, количество участников и количество проектов, если эти значения присутствуют в ответе backend.

[H3] Active workspace
Хук useActiveWorkspace объединяет данные из /auth/init, список workspaces и сохраненный workspace id из localStorage. Выбор активного workspace происходит в порядке приоритета: сохраненный id, default_workspace_id из init response, первый доступный workspace.

Если выбранный workspace исчезает или становится недоступен, frontend может откатиться к другому workspace из списка. Это важно для командного продукта, потому что пользователь может быть удален из workspace или workspace может быть изменен владельцем.

[H3] Wizard создания рабочего пространства
Создание workspace реализовано как трехшаговый wizard в WorkspaceLandingPage. На первом шаге пользователь вводит название, описание и выбирает accent color. На втором шаге он может добавить приглашения участников с email и ролью. На третьем шаге отображается review созданной конфигурации.

При отправке формы useCreateWorkspace вызывает POST /workspaces/create. После создания workspace отправляются invite-запросы через useCreateWorkspaceInvite. Для приглашений используется Promise.allSettled, чтобы частичная ошибка invite не ломала создание самого workspace. Если часть приглашений не отправилась, пользователь получает warning notification.

После успешного создания frontend устанавливает новый workspace как активный и переводит пользователя на /workspace. Это делает flow завершенным: пользователь не остается на странице создания, а сразу попадает в рабочую область.

[H3] Workspace shell
WorkspaceShell отображает отдельный sidebar для workspace-разделов. В нем есть logo, initials/avatar, имя пользователя, handle, selector active workspace, навигация по workspace pages и logout. Если workspace несколько, показывается select; если workspace один, отображается его имя без лишнего dropdown.

Такой shell отделяет командные разделы от общего dashboard/sidebar. Это улучшает навигацию: пользователь понимает, что projects, members, history, pricing и integrations относятся к выбранному workspace, а не ко всему аккаунту сразу.

[H2] Project creation и workspace projects

[H3] UI страницы проектов
WorkspaceProjectsPage отображает проекты в виде карточек. В карточке есть название, описание, количество задач, progress bar, кнопка открытия и menu button. Также реализован поиск по title и description, чтобы пользователь мог быстро найти нужный проект в рабочем пространстве.

Текущая страница сохраняет visual structure через WORKSPACE_PROJECTS, но API-слой уже подготовлен отдельно. Такое разделение позволило сначала построить устойчивый интерфейс карточек, а затем подключать backend CRUD без переработки всей верстки.

[H3] API hooks для проектов
Для проектов добавлены API constants PROJECTS_API и hook-слой useWorkspaceProjects, useCreateProject, useUpdateProject и useDeleteProject. Список проектов запрашивается через GET /workspaces/{workspace_id}/projects, а создание отправляет workspace_id, title и description.

Все project mutations инвалидируют queryKeys.projects(workspaceId). Это важно, потому что после создания, обновления или удаления проекта список должен возвращаться к server-truth состоянию. Если active workspace не выбран, useCreateProject бросает ApiError с полем workspace_id, чтобы UI мог показать понятную ошибку выбора workspace.

[H2] Roadmaps

[H3] Загрузка дорожных карт в контексте workspace
Roadmaps загружаются через useRoadmaps. Hook берет active workspace из useActiveWorkspace и отправляет GET /roadmaps/ с параметром workspace_id. Query включается только когда workspace готов, поэтому компонент не делает некорректный запрос без workspace context.

Ответ backend unwrap-ится через unwrapApiData. При ошибке выбора workspace используется notification, чтобы пользователь видел конкретное действие: сначала выбрать рабочее пространство, затем работать с дорожными картами.

[H3] Timeline layout
RoadmapsPage строит timeline из месяцев и недель. Минимальный диапазон начинается примерно за месяц до текущей даты, максимальный - на несколько месяцев вперед. Если backend возвращает roadmaps с started_at и deadline за пределами этого окна, диапазон расширяется по фактическим датам.

Для каждой roadmap вычисляются startWeek и durationWeeks. Расчет основан на месячном смещении относительно startDate и переводе месяца в четыре недели. Это упрощенная модель, но она достаточна для текущего визуального планирования и хорошо ложится на сетку month/week.

[H3] Создание и редактирование roadmap
RoadmapCreateModal используется и для создания, и для редактирования. В create mode пользователь вводит title, description, deadline и color. При submit deadline переводится в ISO string, а payload отправляется через useCreateRoadmap. При edit mode отправляется roadmapId и измененные поля через useUpdateRoadmap.

После create/update выполняется invalidation queryKeys.roadmaps(workspaceId), поэтому timeline обновляется из backend. В payload также передается workspace_id, чтобы дорожная карта была привязана к текущему workspace, а не создавалась в неопределенном контексте.

[H3] Roadmap tasks и визуальные карточки
RoadmapGroup показывает дорожную карту как строку timeline с цветной полосой, названием, статусом и вложенными notes, если они есть в ответе backend. Это позволяет видеть связь между roadmap и задачами, не открывая Kanban.

Текущая реализация использует fallback значения для статуса и tag, если backend их не вернул. Такой подход сохраняет устойчивость интерфейса на переходном API-контракте.

[H2] Tasks Kanban page и редактирование задач

[H3] Загрузка statuses, notes и roadmaps
TasksPage объединяет несколько источников данных: statuses из /statuses/, notes из /notes/ и roadmaps из useRoadmaps. Все запросы выполняются в контексте active workspace. После загрузки statuses и notes компонент группирует notes по status_id и строит Kanban columns.

Каждая note превращается в task card с id, title, description, columnId и roadmapName. RoadmapName вычисляется по roadmap_id, чтобы карточка задачи могла показывать связь с дорожной картой.

[H3] Создание задачи через modal
Создание задачи выполняется через Kanban modal. Пользователь вводит заголовок, rich text описание, deadline и выбирает roadmap. При submit TasksPage собирает payload: title, content, deadline, label_id, roadmap_id, status_id и workspace_id.

Если workspace не выбран, frontend показывает notification и не отправляет некорректный запрос. После успешного POST /notes/create выполняется invalidation queryKeys.notes(workspaceId), чтобы Kanban получил свежие данные с backend.

[H3] Drag-and-drop и изменение статуса
Kanban использует react-beautiful-dnd. При завершении drag-and-drop TasksPage проверяет destination. Если карточка перемещена в другую колонку, frontend находит исходную note, собирает payload с title, content, status_id и workspace_id, затем отправляет PUT /notes/{noteId}.

После успешного обновления статуса выполняется invalidation notes query. Это делает backend источником истины: UI может локально переместить карточку, но окончательное состояние подтверждается повторной загрузкой notes.

[H3] Редактирование задачи и details mode
KanbanModalView поддерживает режимы create, edit и details. В details mode задача открывается для просмотра, а кнопка Редактировать переводит modal в edit mode. В edit mode используется та же форма, что и при создании, но с другими title и submit label.

В useKanban реализована локальная логика onEditTask, которая обновляет задачу в Kanban reducer и закрывает modal. [H3] Создание статусов как Kanban-колонок

Это расширяет Kanban не только задачами, но и структурой workflow. Пользователь может добавлять собственные колонки, а не работать только с заранее заданными статусами.

[H2] API, состояние и обработка ошибок

[H3] Централизация API endpoints
API constants находятся в src/consts/api.ts. В них описаны AUTH_API, WORKSPACES_API, USER_API, STATUSES_API, NOTES_API, ROADMAPS_API и PROJECTS_API. Такой подход уменьшает количество hardcoded endpoint strings в компонентах и hooks.

Для каждого endpoint хранится METHOD и URL. URL может быть строкой или функцией от id, например /workspaces/{workspace_id}/projects, /projects/{project_id}, /roadmaps/{roadmapId} и /notes/{noteId}.

[IMAGE]
Рисунок 26 - Место для фрагмента кода API constants

[H3] Query keys и invalidation
Query keys вынесены в src/consts/query-keys.ts. В них есть ключи для auth init, workspaces, workspace, statuses, notes, roadmaps, labels, projects, members, dashboard summary и current time tracking.

После mutations используется queryClient.invalidateQueries. Для workspace-scoped данных invalidation выполняется с workspaceId, например queryKeys.projects(workspaceId), queryKeys.notes(workspaceId), queryKeys.statuses(workspaceId) и queryKeys.roadmaps(workspaceId). Это защищает данные разных workspaces от смешивания в одном cache key.

[H3] Envelope responses и ApiError
Frontend работает с API responses через assertApiSuccess и unwrapApiData. Это нужно потому, что часть endpoints может возвращать bare array, а часть - envelope с success/message/data. Утилиты скрывают эти различия от компонентов.

Для ошибок используется ApiError. Он может содержать errors, например workspace_id: Workspace selection is required. Компоненты и hooks проверяют такие ошибки и показывают notification, вместо того чтобы оставлять пользователя с неизвестной причиной сбоя.

[H2] Тестирование и проверка качества

[H3] Unit и component tests
В проекте используются Jest, Testing Library и jsdom environment. Для моей frontend области важны тесты Application, token helpers, API response helpers, workspace routes, WorkspaceShell, WorkspaceLandingPage, useWorkspaces, useActiveWorkspace, useWorkspaceProjects, WorkspaceProjectsPage, WorkspaceIntegrationsPage, WorkspacePricingPage, WorkspaceHistoryPage, useTasksData, useRoadmaps и RoadmapCreateModal.

Эти тесты проверяют не только rendering, но и поведение hooks: выбор active workspace, отправку workspace-scoped запросов, обработку missing workspace errors, invalidation после mutations и корректную работу UI states.

[H3] E2E tests
E2E tests находятся в e2e/auth.e2e.ts, e2e/example.e2e.ts и e2e/roadmaps.e2e.ts. Они используют Selenium WebDriver и требуют локально поднятый frontend, backend и browser driver. Эти тесты полезны для ручной регрессии основных пользовательских сценариев, но требуют подготовленного окружения.

[H3] Lint и build
Lint выполняется через yarn lint и использует @steroidsjs/eslint-config/frontend. Production build выполняется через yarn build. Эти проверки дополняют тесты: lint помогает находить стилевые и часть статических ошибок, а build проверяет, что webpack pipeline может собрать приложение для deployment.

[H3] Текущие ограничения качества
В проекте пока нет отдельного typecheck script через tsc --noEmit, а strict mode в TypeScript не включен. Это увеличивает риск ошибок в местах, где backend response имеет переходную форму или где используются any.

CI запускает lint и build, но unit/e2e tests не являются обязательным gate на текущем pipeline. Следующим шагом я считаю подключение yarn test в CI после lint/build и отдельную стабилизацию e2e окружения для auth, roadmaps и workspace flows.
