[H2] 3 Ход работы
Работа выполнялась на базе существующего учебного SSR-магазина на Express и EJS. Последний коммит b91f7eb4cc834acedd51b239c3cf348b40294441 с сообщением lab 5 done добавил WebSocket-чат, клиентский виджет и тестовые сценарии. В качестве WebSocket-библиотеки выбрана ws, что отражено в package.json и package-lock.json.

[H3] 3.1 Настройка WebSocket-сервера
WebSocket-сервер вынесен в отдельный модуль src/websocket/server.js. Он создается как WebSocketServer с параметром noServer: true, поэтому подключение выполняется через событие upgrade основного HTTP-сервера. Такой подход позволяет использовать тот же порт, что и Express-приложение, и явно направлять WebSocket-запросы только на путь /ws/chat.

В src/server.js основной Express app оборачивается в http.createServer, после чего вызывается attachChatServer(server, sessionMiddleware). При запуске сервер выводит адрес HTTP-приложения и WebSocket endpoint. Для ограничения подключений реализована проверка Origin: если заголовок Origin указан, его host должен совпадать с host текущего запроса. Это закрывает подключение с постороннего домена и сохраняет возможность локальных и серверных подключений без Origin.

[H3] 3.2 Управление подключениями и аутентификацией
При успешном WebSocket upgrade к запросу применяется Express sessionMiddleware. Если в сессии есть req.session.user, клиент считается авторизованным, а в чат передаются его id и name. Если пользователь не авторизован, подключение разрешается в гостевом режиме: сервер создает guest-id на основе randomUUID и имя вида Гость-XXXX. В текущей модели пользователя проекта отдельное поле аватара не хранится, поэтому в WebSocket-сообщения передаются идентификатор, имя и признак isGuest.

Каждое подключение получает socketId через randomUUID. Сервер сохраняет объект подключения в Map connections, фиксирует socketId, пользователя, комнату, IP-адрес, время подключения connectedAt и флаг isAlive для heartbeat-проверки. При подключении клиент получает событие welcome с socketId, данными пользователя и списком доступных комнат. В журнал выводятся socketId, IP, user id, имя пользователя, гостевой статус и время подключения.

[H3] 3.3 Реализация комнат и истории сообщений
Комнаты вынесены в src/websocket/rooms.js. В модуле определены четыре предустановленных канала: general - Общий чат, support - Техническая поддержка, products-discussion - Обсуждение товаров, random - Случайная комната. Для проверки корректности комнаты используется ROOM_INDEX, а для получения списка комнат - функция getRooms.

История сообщений хранится отдельно для каждой комнаты в памяти процесса. Константа HISTORY_LIMIT равна 50, поэтому после добавления нового сообщения старые записи сверх лимита удаляются. Дополнительно реализована загрузка и сохранение истории в src/data/chat-history.json. Запись на диск выполняется с debounce 500 мс, а при завершении сервера вызывается flushNow, чтобы не потерять последние сообщения.

[H3] 3.4 Обработка входящих событий
Сервер принимает сообщения в формате JSON-обертки с полями type и payload. Невалидный JSON, отсутствие type или неизвестный тип события приводят к отправке события error. Для поддерживаемых событий реализованы отдельные обработчики внутри attachChatServer.

[TABLE_START]
[TABLE_CAPTION] Таблица 2 - Обработка входящих событий
| Событие | Действие сервера |
| join_room | Проверяет существование комнаты, переводит клиента из прежней комнаты, отправляет историю и online_users |
| leave_room | Проверяет текущую комнату и рассылает user_left участникам прежней комнаты |
| send_message | Проверяет комнату, членство клиента и непустой текст, создает сообщение и рассылает message |
| typing | Передает typing_status другим участникам текущей комнаты |
| get_online_users | Возвращает список пользователей выбранной комнаты через online_users |
[TABLE_END]

Сообщения имеют поля id, room, socketId, userId, userName, isGuest, text и sentAt. Для текста задано ограничение MAX_TEXT_LENGTH 2000 символов. Пустые сообщения, отправка в несуществующую комнату и отправка без предварительного входа в комнату обрабатываются как ошибки с кодами INVALID_PAYLOAD, UNKNOWN_ROOM или NOT_IN_ROOM.

[H3] 3.5 Рассылка исходящих событий
Для рассылки используется функция broadcast, которая проходит по Map подключений и отправляет сообщение только клиентам выбранной комнаты. При необходимости можно исключить отправителя, например для typing_status. Отдельная функция safeSend проверяет состояние сокета перед отправкой, чтобы не писать в закрытое соединение.

[TABLE_START]
[TABLE_CAPTION] Таблица 3 - Исходящие события сервера
| Событие | Когда отправляется |
| welcome | После успешного WebSocket-подключения |
| history | После входа клиента в комнату или повторного join_room в ту же комнату |
| message | После успешного send_message |
| user_joined | После успешного join_room |
| user_left | При leave_room, переключении комнаты или отключении клиента |
| typing_status | После получения typing от участника комнаты |
| online_users | После запроса списка пользователей и при изменении состава комнаты |
| error | При некорректном payload, неизвестной комнате, неизвестном типе события или нарушении состояния |
[TABLE_END]

[H3] 3.6 Корректное завершение и устойчивость соединений
Для контроля живых клиентов добавлен heartbeat с интервалом 30 секунд: сервер отправляет ping, ожидает pong и завершает неответившие подключения через terminate. При остановке процесса SIGINT или SIGTERM вызывается shutdown в src/server.js. Он закрывает WebSocket-подключения с кодом 1001, останавливает WebSocketServer, сохраняет историю сообщений и затем закрывает HTTP-сервер. Для аварийной ситуации предусмотрен таймер принудительного выхода через 5 секунд.

На клиентской стороне в public/scripts/chat-widget.js реализовано автоматическое переподключение. После потери соединения виджет показывает статус ошибки и повторяет подключение с нарастающей задержкой 1, 2, 4, 8 и 16 секунд. После восстановления соединения клиент снова входит в выбранную комнату.

[H3] 3.7 Интеграция клиентского виджета
Пользовательский интерфейс чата вынесен в partial views/partials/chat-widget.ejs. Виджет содержит кнопку открытия, выбор комнаты, список онлайн-пользователей, ленту сообщений, индикатор набора текста и форму отправки сообщения. Скрипт public/scripts/chat-widget.js подключается вместе с partial и работает с endpoint /ws/chat на текущем host, выбирая ws или wss по протоколу страницы.

Стили виджета вынесены в public/styles/chat.css и подключены в views/partials/head.ejs. Сам виджет добавлен в общий footer partial, поэтому чат доступен на страницах приложения без дублирования разметки в отдельных шаблонах. Клиент экранирует HTML в пользовательских сообщениях, отображает сообщения текущего пользователя отдельно и обновляет список онлайн-участников по событию online_users.

[H3] 3.8 Проверка реализации
В файл test/app.test.js добавлены автоматизированные проверки WebSocket-функциональности. Тесты запускают HTTP-сервер на свободном порту, подключают клиентов через ws, проверяют welcome, join_room, history, online_users, broadcast сообщений между участниками, работу авторизованного пользователя через cookie ssr-store.sid, ошибку UNKNOWN_ROOM, событие user_left, выдачу истории новым участникам и наличие виджета на странице.

Локальный запуск npm test в рабочем окружении был начат после анализа коммита, однако завершился ошибкой Cannot find module ws, так как в текущей папке отсутствуют установленные node_modules с новой зависимостью. Поэтому в рамках отчета зафиксировано наличие тестовых сценариев в коде, но прохождение тестов в данном окружении не утверждается.

[H2] 4 Вывод
В результате работы WebSocket-сервер был интегрирован в существующее Express-приложение и получил endpoint /ws/chat на общем HTTP-сервере. Реализованы тематические комнаты, обработка основных событий чата, рассылка сообщений и служебных уведомлений, список онлайн-пользователей, гостевой режим, использование текущей cookie-сессии для авторизованных пользователей, ограниченная история сообщений и корректное завершение работы.

Практическая часть показала, что WebSocket удобно использовать для сценариев, где сервер должен немедленно передавать изменения нескольким клиентам без постоянных HTTP-запросов. Разделение логики на server.js и rooms.js упростило поддержку подключения, событий и истории сообщений, а клиентский виджет продемонстрировал полный цикл обмена данными в реальном времени: подключение, вход в комнату, отправку сообщений, получение уведомлений, индикацию набора текста и переподключение после разрыва связи.
