[H1] Отчёт по доработке SSR-приложения интернет-магазина: реализация REST API

[H2] 1. Цель

Целью работы являлось освоение принципов проектирования и реализации RESTful API в существующем SSR-приложении интернет-магазина. В рамках задания требовалось организовать серверные эндпоинты для работы с товарами, корзиной, пользователями и заказами, обеспечить обмен данными в формате JSON, а также интегрировать новые API-возможности в уже созданный серверный интерфейс без перехода к полноценному SPA-подходу.

[H2] 2. Задачи

Для достижения поставленной цели были поставлены следующие задачи: подключить обработку JSON-запросов в Express-приложении и вынести REST-маршруты в отдельные модули; реализовать API каталога товаров и категорий на базе существующего сервисного слоя; добавить API регистрации, входа, выхода и получения текущего пользователя с использованием той же системы сессий, что и в SSR-части; разработать API корзины и оформления заказов с обязательной проверкой авторизации; внедрить серверную валидацию входных данных и унифицированные JSON-ответы с корректными HTTP-статусами; связать REST API со страницей корзины так, чтобы изменения могли отображаться без полной перезагрузки страницы; расширить набор интеграционных тестов, подтверждающих работоспособность как SSR-маршрутов, так и новых API-эндпоинтов.

[H2] 3. Ход работы

[H3] 3.1 Проектирование и реализация API каталога

На первом этапе была расширена конфигурация приложения в файле app.js. Помимо уже существующего разбора HTML-форм через express.urlencoded, был подключён middleware express.json, после чего новые маршруты API были вынесены в отдельные модули и смонтированы с общим префиксом /api. Дополнительно в проект был добавлен документ проектирования REST API, в котором были зафиксированы ключевые эндпоинты, ожидаемые форматы запросов и коды ответов. Такое решение позволило отделить JSON-интерфейс от SSR-маршрутов и сохранить модульную структуру приложения.

Для работы с данными каталога был создан модуль productApiRoutes.js, который переиспользует уже существующий catalogService.js. Благодаря этому логика хранения и выборки товаров не дублируется: API-слой только принимает параметры запроса, вызывает сервисные функции и возвращает результат через res.json. Для обработки ошибок был введён общий помощник sendApiError, который формирует унифицированный ответ вида error.code и error.message. Если товар или категория не найдены, сервер возвращает код 404 и JSON-описание ошибки вместо HTML-страницы, что соответствует требованиям REST API.

[H3] 3.2 Реализация API аутентификации, корзины и заказов

На втором этапе были реализованы маршруты authApiRoutes.js, cartApiRoutes.js и orderApiRoutes.js. Для аутентификации REST API была сохранена та же система серверных сессий, что и в SSR-приложении, поэтому состояние пользователя и содержимое корзины остаются общими для HTML-страниц и JSON-запросов. В отдельный модуль sessionService.js были вынесены операции регенерации, сохранения и уничтожения сессии. При входе пользователя в систему корзина сохраняется, а в сессию помещается только безопасная информация о пользователе без passwordHash, что дополнительно снижает риск утечки чувствительных данных.

Для защиты приватных маршрутов был добавлен middleware requireApiAuth, который возвращает JSON-ошибку 401 Unauthorized, если пользователь не авторизован. Серверная валидация входных данных была централизована в validators.js. В нём реализованы проверки обязательных полей, нормализация email и контроль того, что quantity является положительным целым числом. Благодаря этому POST /api/auth/register, POST /api/auth/login, POST /api/cart/items и PUT /api/cart/items/:productId корректно обрабатывают неверные входные данные и возвращают 400 Bad Request с объяснением ошибки. Для сценариев недостаточных прав и отсутствующих сущностей также используются коды 403 Forbidden и 404 Not Found.

Отдельно был реализован модуль orderService.js, обеспечивающий запись заказов в файл orders.json и выборку истории заказов по идентификатору пользователя. Маршрут POST /api/orders создаёт заказ на основе текущего состояния корзины, вычисляет итоговую сумму, сохраняет timestamp и после успешного оформления очищает session.cart. Маршрут GET /api/users/:id/orders позволяет получить историю заказов только владельцу соответствующего профиля. Таким образом, серверный REST API охватывает не только операции чтения, но и полный прикладной цикл: авторизация, изменение корзины, оформление заказа и последующий просмотр истории.

[H3] 3.3 Интеграция REST API в SSR-интерфейс и тестирование

На третьем этапе REST API был встроен в уже существующий SSR-интерфейс корзины. В шаблоне cart.ejs появились data-атрибуты, связывающие серверно отрисованные формы с API-маршрутами, а в header.ejs счётчик корзины был обёрнут в отдельный элемент data-cart-count для последующего обновления на клиенте. Для авторизованного пользователя подключается скрипт public/scripts/cart-page.js, который перехватывает отправку форм, выполняет fetch-запросы к /api/cart и /api/orders, а затем локально перерисовывает список товаров, итоговую сумму и сообщения об ошибках или успешных действиях. При этом SSR-маршруты cartRoutes.js были сохранены, поэтому приложение продолжает корректно работать и без клиентского JavaScript, а REST API выступает как прогрессивное улучшение интерфейса.

Дополнительно была доработана логика серверной корзины в cartService.js: теперь в ней выделены функции поиска позиции, обновления количества, полной очистки и построения агрегированного состояния корзины с totalAmount и totalQuantity. Такое представление используется одновременно и SSR-шаблоном, и JSON-ответами API, что устраняет расхождения между двумя способами отображения данных. Для стабильной работы в режиме разработки был также добавлен файл nodemon.json, исключающий src/data/*.json из отслеживания. Это важно, потому что записи в users.json и orders.json происходят во время работы приложения, и лишний рестарт сервера мог бы сбрасывать текущее состояние памяти и мешать отладке сценариев сессий.

Завершающим этапом стало расширение integration-набора test/app.test.js. Проверки охватывают старые SSR-сценарии и новые REST-эндпоинты: получение каталога в JSON, обработку 404 для несуществующего товара, регистрацию и вход через API, выход и проверку /api/auth/me, все операции корзины, оформление заказа, запрет просмотра чужой истории заказов, а также наличие клиентских API-hook'ов на странице корзины. Отдельным тестом подтверждено, что конфигурация nodemon не следит за изменяемыми JSON-файлами. В результате запуск npm test завершился успешно: пройдено 26 интеграционных тестов, что подтверждает работоспособность реализованного REST API и его корректную интеграцию в существующее SSR-приложение.
