[H2] 1 Цель
Цель работы - реализовать в учебном SSR-приложении push-уведомления пользователя по подписке с использованием стороннего сервера push-нотификаций Firebase Cloud Messaging. В отличие от имитации через WebSocket, такая схема должна позволять доставлять уведомления через инфраструктуру FCM и получать их даже в ситуациях, когда вкладка приложения не является активной.

Реализация анализировалась по последнему коммиту 8bf54a33c2596d8c29f89f747ff083d50548a542 с сообщением lab 8 done. Коммит добавил серверную интеграцию Firebase Admin SDK, клиентскую регистрацию FCM-токена, хранение подписок, Firebase service worker и триггеры отправки уведомлений при событиях на стороне сервера.

[H2] 2 Задачи
Для достижения цели были поставлены следующие задачи: подключить Firebase Cloud Messaging к существующему Express-приложению; описать конфигурацию Firebase для серверной и клиентской частей; реализовать клиентскую подписку на push-уведомления и получение FCM-токена; сохранить токен и выбранные темы подписки на сервере; реализовать серверную отправку уведомлений подписчикам; добавить триггеры уведомлений при событиях приложения; сохранить совместимость с ранее реализованным WebSocket-механизмом и fallback-отображением уведомлений; проверить основные сценарии автоматизированными тестами.

[H2] 3 Ход работы
Работа выполнялась на базе существующего приложения SSR Store на Node.js, Express и EJS. Предыдущая лабораторная работа уже содержала виджет выбора топиков, WebSocket-канал /ws/push и отображение уведомлений через Service Worker или toast. В коммите lab 8 done эта функциональность была расширена настоящей Web Push-интеграцией через Firebase Cloud Messaging.

[H3] 3.1 Подготовка конфигурации Firebase
Для конфигурации Firebase добавлен файл src/config/firebaseConfig.js. Он читает переменные окружения для серверной части Firebase Admin SDK и для клиентского Web App config. Серверные учетные данные включают projectId, clientEmail и privateKey, причем privateKey нормализуется из строки окружения с последовательностями \n в обычные переводы строк. Клиентская часть использует apiKey, authDomain, projectId, messagingSenderId, appId и публичный VAPID-ключ.

В корне проекта добавлен файл .env.example, который показывает набор необходимых переменных окружения. В package.json добавлены зависимости dotenv и firebase-admin. В src/server.js подключается require('dotenv').config(), после чего вызывается fcmService.init(). Если конфигурация неполная, сервис выводит в лог сообщение о выключенном FCM-режиме и приложение продолжает работать с WebSocket-уведомлениями. Если все переменные заданы, Firebase Admin SDK инициализируется и сервер получает объект messaging для отправки push-сообщений.

[H3] 3.2 Реализация серверного FCM-сервиса
Основная серверная логика вынесена в src/services/fcmService.js. Модуль хранит состояние enabled, объект messaging, клиентскую конфигурацию и тестовые hooks. Метод init загружает конфигурацию, подключает firebase-admin, создает Firebase app при необходимости и сохраняет admin.messaging(). Для внешних модулей предоставлены методы isEnabled, getWebConfig, sendToTokens, sendToTopic и sendToUser.

Метод buildMessage формирует FCM-сообщение для конкретного токена. В него входят notification с title и body, data с url, topic и sentAt, а также webpush-настройки с fcmOptions.link и параметрами notification. Благодаря этому уведомление содержит текст для системного отображения и данные для перехода по URL при клике.

Метод sendToTokens отправляет массив сообщений через messaging.sendEach. Если FCM отключен или список токенов пуст, метод безопасно возвращает нулевые счетчики. При ошибках с невалидными регистрационными токенами сервис собирает такие токены и удаляет их из локального хранилища подписок. Это уменьшает накопление устаревших записей и делает последующие рассылки чище.

[H3] 3.3 Хранение подписок и API клиента
Для хранения подписок добавлен файл src/services/pushSubscriptionService.js и JSON-хранилище src/data/push-tokens.json. Запись подписки содержит token, userId, topics, userAgent, createdAt и updatedAt. Сервис умеет создавать или обновлять запись по токену, удалять один или несколько токенов, находить подписки по топику, находить подписки конкретного пользователя по топику и возвращать полный список записей.

HTTP API подписок реализован в src/routes/api/pushApiRoutes.js и подключен в src/app.js по префиксу /api. Endpoint GET /api/push/config возвращает Firebase web-config и список разрешенных топиков, если FCM включен. Если конфигурация отсутствует, он возвращает ошибку 503 с кодом FCM_DISABLED. Endpoint POST /api/push/subscribe принимает token и topics, валидирует длину токена и допустимость топиков, привязывает userId из текущей сессии при наличии авторизации и сохраняет подписку. Endpoint DELETE /api/push/subscribe удаляет токен из хранилища.

Список допустимых топиков переиспользует ALLOWED_TOPICS из WebSocket push-сервера: promotions, orders, news и system. Это сохраняет единую модель подписок для WebSocket-имитации и FCM-уведомлений, поэтому пользователь выбирает темы один раз, а приложение синхронизирует их с обоими механизмами доставки.

[H3] 3.4 Клиентская подписка и получение FCM-токена
Клиентская часть FCM добавлена в public/scripts/push/fcm-client.js. Скрипт загружает Firebase Web SDK из CDN, запрашивает конфигурацию через /api/push/config, регистрирует service worker /firebase-messaging-sw.js и инициализирует Firebase app с именем fcm-client. После выдачи браузером разрешения на уведомления он вызывает getToken с VAPID-ключом и serviceWorkerRegistration, получает FCM-токен и отправляет его на сервер вместе со списком выбранных топиков.

Существующий public/scripts/push/push-client.js был доработан для совместной работы с FCM. При сохранении подписок и наличии разрешения granted он лениво импортирует /scripts/push/fcm-client.js. После подтверждения подписки через WebSocket виджет генерирует событие push:topics-changed, а FCM-клиент слушает это событие и синхронизирует токен с сервером. Если пользователь снимает все темы, FCM-клиент вызывает deleteToken и отправляет DELETE /api/push/subscribe для удаления записи подписки.

Для foreground-сообщений используется onMessage: когда вкладка активна, входящее FCM-сообщение отображается как toast внутри страницы. Это согласуется с уже существующим визуальным fallback-механизмом и позволяет не дублировать пользовательский интерфейс уведомлений.

[H3] 3.5 Firebase service worker и фоновые уведомления
Для фонового получения push-уведомлений добавлен public/firebase-messaging-sw.js. В src/app.js создан отдельный маршрут /firebase-messaging-sw.js, который отдает этот файл с Service-Worker-Allowed: / и Cache-Control: no-cache. Клиент регистрирует worker с параметрами Firebase config в query string, чтобы worker мог инициализировать Firebase app в service worker context.

Внутри service worker подключаются firebase-app-compat.js и firebase-messaging-compat.js. После инициализации Firebase вызывается firebase.messaging(), а обработчик onBackgroundMessage формирует уведомление из payload.notification и payload.data. Для отображения используется self.registration.showNotification с title, body, tag, icon, badge и data. При клике по уведомлению обработчик notificationclick закрывает уведомление, ищет уже открытое окно с нужным адресом и фокусирует его или открывает новое окно.

Таким образом клиент может получать push-уведомления как в активной вкладке через onMessage, так и в фоне через Firebase service worker. Это является ключевым отличием от простой WebSocket-имитации, которая работает только при активном соединении клиента с сервером.

[H3] 3.6 Серверные триггеры отправки уведомлений
В коммите добавлено несколько серверных триггеров FCM. При создании заказа через POST /api/orders в src/routes/api/orderApiRoutes.js сервер вызывает fcmService.sendToUser для владельца заказа с топиком orders, заголовком Заказ оформлен, суммой заказа и ссылкой /profile. Аналогичная логика добавлена в SSR-маршрут /cart/checkout в src/routes/cartRoutes.js.

При регистрации нового пользователя через API-маршрут /api/auth/register и SSR-маршрут /register сервер вызывает fcmService.sendToTopic для топика system. В payload передается сообщение о новом пользователе, а в параметрах указывается excludeUserId, чтобы не отправлять это уведомление самому только что зарегистрированному пользователю.

В WebSocket-чате src/websocket/server.js после успешной отправки сообщения дополнительно формируется короткий preview текста. Сервер рассылает событие message_notify WebSocket-клиентам вне комнаты отправленного сообщения и параллельно вызывает fcmService.sendToTopic для топика news. Отправитель исключается из FCM-рассылки, если это авторизованный пользователь. Это реализует сценарий уведомления о сообщении от другого пользователя.

Административная форма /admin/notify также расширена. Она по-прежнему отправляет WebSocket push через pushService.broadcast, но теперь дополнительно запускает fcmService.sendToTopic для выбранного топика. Поэтому ручная рассылка администратора доставляется и по открытому WebSocket-каналу, и через Firebase подписчикам, у которых сохранены FCM-токены.

| Событие | Топик | Получатели |
| Оформление заказа | orders | Токены владельца заказа, подписанные на orders |

[H3] 3.7 Совместимость с WebSocket-уведомлениями
Реализация FCM не заменила предыдущий WebSocket-механизм, а дополнила его. Виджет подписок продолжает подключаться к /ws/push, сохранять выбранные топики в localStorage и получать события push через WebSocket. FCM-клиент использует те же сохраненные топики и синхронизирует их с сервером через HTTP API.

Такой подход дает два режима доставки. WebSocket обеспечивает мгновенное уведомление при открытой вкладке и не требует внешней Firebase-конфигурации. FCM обеспечивает настоящую push-доставку через сторонний сервер, если проект настроен и пользователь выдал разрешение браузера. При отключенном FCM приложение остается работоспособным: /api/push/config возвращает FCM_DISABLED, FCM-клиент не активируется, а WebSocket-уведомления продолжают работать.

[H3] 3.8 Проверка реализации
Для проверки добавлены автоматизированные тесты в test/app.test.js. Они проверяют ответ GET /api/push/config при отключенном FCM, сохранение токена и топиков для гостевой сессии, отклонение неизвестного топика, привязку userId для авторизованного пользователя, обновление топиков существующего токена и удаление подписки. Также тестируются серверные триггеры: создание заказа должно вызвать отправку пользователю по топику orders, а регистрация пользователя должна вызвать отправку в system с исключением нового пользователя.

Дополнительно проверяется WebSocket-событие message_notify: клиент вне комнаты получает уведомление о сообщении, а клиент в той же комнате не получает лишний notify. Это подтверждает, что сервер различает обычную доставку сообщения участникам комнаты и уведомление пользователей вне контекста текущего диалога.

Локальный запуск npm test в рабочем окружении завершился успешно: прошло 59 тестов. Это подтверждает, что добавленные FCM API, хранение подписок, серверные триггеры и совместимость с существующими сценариями приложения работают в автоматизированной проверке.

[H2] 4 Вывод
В результате работы в проект была добавлена интеграция со сторонним push-сервером Firebase Cloud Messaging. Клиент получил возможность подписываться на уведомления, получать FCM-токен, сохранять выбранные топики на сервере и принимать уведомления как в активной вкладке, так и через Firebase service worker в фоне. Сервер получил конфигурационный слой Firebase, сервис отправки уведомлений, API управления подписками и JSON-хранилище токенов.

Поставленные задачи выполнены: клиентская подписка реализована через Firebase Web SDK и существующий виджет уведомлений; серверная рассылка реализована через Firebase Admin SDK; уведомления отправляются по реальным серверным триггерам - оформлению заказа, регистрации пользователя, сообщению в чате и административной рассылке. При этом сохранена совместимость с WebSocket-режимом, поэтому приложение может работать как с FCM, так и без него.
